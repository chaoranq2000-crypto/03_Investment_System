## Objective and completion semantics

### Fixed objective

在不修改正式 portfolio SQLite、用户现有 review sidecar、v2 candidate sidecar和既有不可变 artifact 的前提下，完成以下七项产品修正：

1. 即使用户没有记录 Decision 或决策原因，也生成可验证的操作事实复盘；决策逻辑复核单独显示 `not_recorded` 或 `not_applicable`，不阻断操作复盘。
2. 仅依据账户数量变迁和事件事实，确定性识别 `position_open`、`position_increase`、`position_reduce`、`position_close`、反转/异常及现金事件；不得把操作分类扩写成投资动机。
3. 分开 `effective_at/occurred_at`、`user_known_at`、`system_observed_at`、`recorded_at/ingested_at` 和各自依据。用户自己的无冲突账户事实按 owner-action policy 视为用户在生效时已知；后来录入不得伪造成系统当时已观察。
4. 从完整同步的只读账本重建事件前、事件后和 checkpoint 时点的持仓状态，并对持仓数量、成本、现金、价格、NAV、权重和行业逐字段报告 `available/partial/missing`；局部缺失不得隐藏已经可证明的持仓。
5. 将 `episode_lifecycle`、`review_kind`、`review_readiness` 和 `outcome_maturity` 分离。开放持仓允许形成 `active_checkpoint`，操作复盘可为 `ready`，结果保持 `interim/not_final`。
6. 在冻结 review input 前先从正式库只读装配本地市场上下文；仅在版本化覆盖检查证明数据缺失、过期或不足时，才由受控前置 provider 补入新 v3 cache，然后把来源、请求、时间和内容哈希一并冻结，把所有可用 market rows 实际传给 `supplemental_sources`；若仍无可用 row，则冻结显式 `missing/failed` market projection 和补齐回执，不静默伪造非空来源。晚取得数据标记为 `reconstructed_public_context` 或等价 retrospective 状态，不冒充 `system_known_at_decision`；renderer、API/UI 和 source replay 不联网。
7. API/UI 分开展示操作复盘、决策背景、持仓/现金估值、市场背景、生命周期和结果成熟度；首屏给自然语言结论，原始 gap code 只在证据抽屉/技术详情中显示。

### Truth boundaries

- `operation_review_ready` 只说明交易、持仓与可得上下文足以完成本次操作事实复盘，不说明决策理由正确，也不代表投资结果好坏。
- `decision_context_complete` 可以为假；没有 Decision/理由只影响决策逻辑复核轴，不降低操作复盘轴。
- `user_known_at` 表示本合同固定的决策者知识视角。对用户自己的无冲突账户事实可使用 owner-action default；它不是系统当时观察的证明。
- `system_observed_at` 只能来自真实采集/导入证据。后来录入的信息不能反向伪造系统 observation time。
- 市场数据的 `effective_at`、公开可用时间、抓取/记录时间和用户是否实际看到是不同事实。v3 不凭公开数据反推用户当时必然看过；执行阶段通过外部 provider 后补的数据默认是 retrospective，除非另有真实的决策前 system-observation 证据。
- `snapshot_ready` 按字段或组件判断；持仓可用不等于现金、NAV、权重或行业时点分类完整。
- `outcome_maturity=interim` 是开放持仓的正常生命周期状态，不是复盘失败或缺口。
- `engineering_complete`、`data_ready_at_recorded_cutoff`、`human_product_acceptance` 和 `production_released` 独立陈述，不得互相替代。

## Checkpoint and resume protocol

1. 每次启动先验证 package、contract hash、工作树、分支、source baseline祖先关系、setup-only scope和instruction chain。setup commit相对 `c3e296661c04b9de35795e2311674b507846d19a` 只能新增 v3 的 `CONTRACT.md` 与 `START_HERE.md`。
2. 首次执行在任何candidate写入前记录正式DB、用户sidecar和v2 candidate的SHA-256、size、quick_check、WAL/SHM状态；任一受保护来源无法只读验证则停止。
3. v3 只创建 `data/db/investment_review_reviewability_v3.sqlite3`；不得复制v2 candidate或用户sidecar。测试fixture使用临时目录，不污染真实candidate。
4. 从最早未被Git checkpoint和验证证据共同证明的phase开始。不得凭START_HERE文本或代码存在跳过phase。
5. 每阶段仅修改allowed paths；完成后运行targeted validators、V-002、`git diff --check`和changed-path审查，更新START_HERE，再显式stage并创建规定checkpoint。
6. 每个checkpoint后要求tracked tree clean。忽略的candidate DB/runtime artifacts必须在checkpoint history列明，禁止误加入Git。
7. 既有canonical artifact保持不变；v3新增versioned projection/adapter。任何兼容迁移都必须additive、显式opt-in、可在新库从零重放。
8. 正式数据变化时，选择并记录稳定cutoff；计数动态测量。若588200历史记录仍存在，使用合同固定的2026-07-17样本；若来源内容漂移或消失，停止C-SNAP-001/C-MKT-002实数据验收并报告source drift，不更换成未授权事实。
9. 若恢复时有未提交更改，只有每个路径都属于next_phase、diff内部一致且动作安全可重跑时才继续；否则hard stop。

At minimum: update `START_HERE.md`, run phase validation, inspect scope, stage explicit paths, create the named checkpoint commit, and require a clean checkpoint before the next phase. On resume, start from the earliest phase whose postconditions are not proven.
